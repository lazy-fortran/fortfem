# API rename candidates and migration audit

This is a bounded inventory for the API reorganization planned in the
roadmap.  It is deliberately an audit, not a rename patch.  The first rule is
to keep `fortfem_api` source-compatible while canonical domain facades are
introduced; a name is not removed until an old/new compile test and an
independent behaviour test exist.

## Baseline observed on the audit branch

The current umbrella is `src/fortfem_api.f90` (3,412 lines and 1,713
`public ::` declarations).  The smaller facades already present under
`src/fortfem_api_*.f90` total 2,902 lines.  The umbrella imports application
contracts, FEEC topology, geometry, assembly, BEM, time integration and
generated products in one module.  This is useful as a compatibility surface,
but it makes name ownership and dependency direction difficult to inspect.

The counts below are literal word-boundary matches in `src`, `test`,
`example`, and `doc` at this revision.  They include declarations and
documentation; the source/test split makes the migration workload auditable.
The counts must be regenerated by the API manifest checker before each rename
slice rather than copied forward by hand.

## Candidate set A: parity entry points

`parity` routines compare a manufactured or alternate path against a reference
and return a report.  `compare_` is therefore the preferred canonical verb;
`diagnose_` is reserved for routines that only classify/measure a state and do
not compare two supplied paths.  Existing `parity` schema strings and report
type names are data contracts and must be versioned separately from Fortran
procedure aliases.

| Current public symbol | Proposed canonical symbol | Defining module | Source / test / docs matches | Derivative companions | Classification and migration note |
| --- | --- | --- | ---: | --- | --- |
| `compare_boundary_operator_parity` | `compare_boundary_operator_parity` | `fortfem_boundary_operator_parity` | 7 / 12 / 2 | `_jvp`, `_vjp` | Implemented as the canonical pre-release spelling; the report type and `fortfem-boundary-parity-1` schema remain unchanged. |
| `compare_larger_domain_solution` | `compare_larger_domain_solution` | `fortfem_larger_domain_parity` | 6 / 5 / 1 | `_jvp` | Implemented as the canonical pre-release spelling; the report type and `fortfem-larger-domain-parity-1` schema remain unchanged. |
| `evaluate_beltrami_two_region_parity` | `compare_beltrami_two_region_residual` | `fortfem_beltrami_parity` | 6 / 3 / 1 | none | Compares assembled H(curl) residual with the independent oracle residual. `validate_beltrami_parity` stays a validator. |
| `evaluate_beltrami_shell_parity` | `compare_beltrami_shell_residual` | `fortfem_beltrami_parity` | 5 / 5 / 1 | none | Same as the two-region path, with an energy/conservation ledger. |
| `compare_sheet_current_representations` | `compare_sheet_current_representations` | `fortfem_sheet_current_parity` | 5 / 3 / 3 | none | Implemented as the canonical pre-release spelling; the fitted/resolved ledger contract remains unchanged. |
| `compare_sheet_current_surface_representations` | `compare_sheet_current_surface_representations` | `fortfem_sheet_current_surface_parity` | 6 / 9 / 0 | `_jvp` | Implemented as the canonical pre-release spelling; the surface quadrature and regularized-layer ledger are unchanged. |
| `evaluate_tree_cotree_iga_parity` | `diagnose_tree_cotree_iga_invariance` | `fortfem_tree_cotree_iga_parity` | 5 / 3 / 0 | none | Tests signed-map invariance of a fixed IGA tree-cotree reduction; `diagnose_` is clearer than `compare_` because there is no external reference field. |

The first implementation slice should add canonical wrappers in the defining
modules and re-export both names from `fortfem_api`.  The wrappers must be
thin calls, so the old and new paths have one implementation and cannot drift.
An old/new equivalence test should compare every output array, report field,
status code, and (where present) JVP/VJP output.  Deprecation comments may be
added after the wrappers have shipped, but compiler-specific deprecation
attributes must not become a build requirement.

### Call-site implications

The boundary-operator family has 10 source matches for each derivative
companion and five test matches for each companion.  The sheet-surface JVP has
five source and two test matches.  These are manageable, but the wrappers must
also update the umbrella `use ... only:` and `public ::` lists.  Do not rename
the files or modules in the same change: downstream users may import
`fortfem_boundary_operator_parity` directly.

## Candidate set B: ambiguous `compute_` verbs

`compute_` currently mixes sampling, assembly, geometric measurement and
diagnostic estimation.  The canonical verb should describe the mathematical
operation, with derivative companions preserved exactly (`_jvp`, `_vjp`).
This set is intentionally staged; the generated FCI kernels remain internal
and are not renamed in the public wrapper slice.

| Current symbol | Proposed canonical symbol | Defining module | Source / test / docs matches | Why the rename is safe to verify |
| --- | --- | --- | ---: | --- |
| `compute_boundary_integral` | `integrate_boundary_flux` | `fortfem_solvers_neumann` (facades: `fortfem_api_solvers_laplacian`, `fortfem_api_solvers`) | 8 / 3 / 0 | Scalar output is a boundary flux integral; a manufactured constant-flux oracle is independent of the implementation. |
| `compute_gradient_indicators` | `estimate_gradient_indicators` | `fortfem_api_mesh` | 5 / 2 / 0 | The routine estimates element indicators used by adaptivity; no caller relies on a generic computation name. |
| `compute_scalar_plot_grid` | `sample_scalar_plot_grid` | `fortfem_api_plot_interpolation` | 5 / 0 / 0 | It samples a function on a display grid, and the pointwise interpolation oracle can be checked independently. |
| `compute_vector_plot_grid` | `sample_vector_plot_grid` | `fortfem_api_plot_interpolation` | 5 / 3 / 0 | Same sampling contract, with vector components and Nédélec/RT interpolation. |
| `compute_interface_scalar_jump_average` | `evaluate_interface_scalar_jump_average` | `fortfem_interface_traces` | 5 / 2 / 1 | Pure trace algebra with a direct plus/minus oracle; `evaluate` matches the vector trace routine. |
| `compute_interface_vector_traces` | `evaluate_interface_vector_traces` | `fortfem_interface_traces` | 5 / 3 / 1 | Pure trace algebra; preserve normal/tangential orientation and signs in the oracle. |
| `compute_fci_parallel_diffusion_diagonal` | `assemble_fci_parallel_diffusion_diagonal` | `fortfem_fci_parallel_operator` | 6 / 3 / 2 | Builds a diagonal operator, so `assemble` communicates ownership and supports generated JVP/VJP naming. |
| `compute_fci_anisotropic_diffusion_diagonal` | `assemble_fci_anisotropic_diffusion_diagonal` | `fortfem_fci_parallel_operator` | 6 / 3 / 2 | Same operator family; generated product names remain internal. |
| `compute_fci_staggered_flux_box_volumes` | `evaluate_fci_staggered_flux_box_volumes` | `fortfem_fci_support_geometry` | 5 / 3 / 2 | Returns geometry measures, not an assembled matrix; its generated value/JVP/VJP products have an independent polygon-volume oracle. |
| `compute_fci_*_cell_areas_2d` | `evaluate_fci_*_cell_areas_2d` | `fortfem_fci_support_geometry` | 5 / 7 / 3 (quadrilateral representative) | Applies uniformly to polygon, curved polygon, Bezier, and quadrilateral variants. Each generated derivative companion must follow the renamed public stem. |

The FCI names must be migrated as a family, not one degree at a time.  The
public wrapper may call `generated_fci_*` unchanged.  Regeneration must be
checked with `tools/codegen/check_generated.sh`; no hand edit to
`src/generated/` is allowed.  The generated module and provenance names are
implementation contracts and should only change in a dedicated generator
version bump.

## Candidate set C: type/constructor consistency

User-facing derived types already follow the `_t` suffix, but constructors
alternate between an unprefixed type stem (`function_space`) and descriptive
mesh factories (`unit_square_mesh`, `mesh_from_boundary`).  The least risky
policy is to add `make_` aliases first, then document one canonical spelling;
the existing short constructors remain compatibility aliases for at least one
major release.

| Existing type | Existing constructor family | Proposed canonical constructor family | Approximate constructor call matches (src + test + example + doc) | Notes |
| --- | --- | --- | ---: | --- |
| `function_space_t`, `vector_function_space_t` | `function_space`, `vector_function_space` | `make_function_space`, `make_vector_function_space` | 14 + 25 | Keep the family parallel; `family` and `degree` validation stays in one implementation. |
| `function_t`, `vector_function_t` | `function`, `vector_function` | `make_function`, `make_vector_function` | 12 + 32 | Avoid a generic `function` export in new domain facades; the old name is especially collision-prone in mixed DSL code. |
| `trial_function_t`, `test_function_t`, vector variants | `trial_function`, `test_function`, `vector_trial_function`, `vector_test_function` | `make_trial_function`, `make_test_function`, and vector counterparts | 11 + 16 + 5 + 6 | Preserve symbolic role types; derivative/JVP APIs do not apply to these constructors. |
| `dirichlet_bc_t`, `vector_bc_t`, `neumann_bc_t` | `dirichlet_bc`, `vector_bc`, `neumann_bc_constant`, `neumann_bc_on_boundary` | `make_dirichlet_bc`, `make_vector_bc`, `make_neumann_bc_constant`, `make_neumann_bc_on_boundary` | 11 + 15 + 3 + 3 | The `make_` prefix removes the current asymmetry without changing BC data layouts. |
| coefficient/source types | `cell_coefficient`, `cell_tensor_coefficient`, `cell_vector_source` | `make_cell_coefficient`, `make_cell_tensor_coefficient`, `make_cell_vector_source` | 7 + 2 + 10 | The tensor constructor is part of the generated tensor-power and anisotropic APIs; preserve exact shapes and provenance. |
| `mesh_t`, `boundary_t` | `unit_square_mesh`, `rectangle_mesh`, `unit_disk_mesh`, `mesh_from_*`, `circle_boundary`, ... | `make_unit_square_mesh`, `make_rectangle_mesh`, `make_unit_disk_mesh`, `make_mesh_from_*`, `make_circle_boundary`, ... | To be measured by manifest before implementation | Do this only after constructor aliases above; mesh naming is user-visible in every example. |

The call-match figures for constructors count `name(` occurrences and include
the defining function.  They are a sizing estimate, not a compatibility
guarantee.  A manifest must distinguish a call from a declaration before a
constructor is renamed.

## Generator, provenance, and schema rules

1. **Public wrappers own names.**  FortSym-generated modules under
   `src/generated/` keep their generator-controlled names.  A public rename
   is an adapter-level change and must not edit generated source.
2. **Derivative closure is mandatory.**  A value routine with `_jvp`, `_vjp`,
   or `_hvp` is one rename unit.  The manifest rejects a canonical value name
   when one companion remains available only under the old stem.
3. **Report schemas are data.**  `schema_version`, `topology_id`, and
   `provenance` strings are not silently changed by a procedure rename.  If a
   report type or serialized field changes, bump its schema and add a fixture
   migration test.
4. **Generated provenance remains reproducible.**  A rename patch records the
   FortSym/FortNum generator revision and reruns the currentness check.  It
   must not regenerate plots, benchmark data, or third-party code as part of
   the API-only change.
5. **No duplicate implementation.**  The canonical procedure calls the old
   implementation (or vice versa) during the transition; tests compare both
   paths.  After the removal release, one implementation remains.

Each agent owns one row and must commit on a worktree branch.  Agents must not
touch another row's files; integration should be done in dependency order.
The first mergeable slices are API-00, API-01, and API-02 because they change
no numerical implementation or generated artifact.

## Required checks for every rename PR

- `fo fmt --check` and `git diff --check`;
- the focused old/new equivalence tests and their independent behavioural
  oracle (not a source-string or repository-state test);
- `fo test` for all touched test targets, with a short timeout for the fast
  manifest/layer checks;
- compile one old-API and one canonical-API smoke program with `fpm`; and
- `tools/codegen/check_generated.sh` when a generated-backed wrapper is
  touched.

Do not remove `fortfem_api` or old spellings in the same patch that introduces
the new facades.  Removal requires a release note, a deprecation window,
downstream example migration, and a clean symbol-manifest diff.
