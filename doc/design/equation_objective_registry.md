# Equation, objective, and constraint registry

`fortfem_equation_objective_registry` is a small, physics-neutral contract for
clients that assemble a residual from several equations, objectives, and
constraints. It is metadata, not an equation compiler: FortFEM does not own
profiles, closures, optimization objectives, equilibrium variables, or
application-specific callbacks.

## Contract

An `equation_objective_block_t` contains:

* a unique, deterministic `name`;
* one of `REGISTRY_KIND_EQUATION`, `REGISTRY_KIND_OBJECTIVE`, or
  `REGISTRY_KIND_CONSTRAINT`;
* a non-negative `row_count` and one-based `row_offset` assigned in declaration
  order;
* caller-owned `units`, `normalization`, and `provenance` tags; and
* `active` and `fixed` flags retained as metadata for the external client.

The registry rejects duplicate names, unknown kinds, missing tags, negative
row counts, inconsistent offsets, and mismatched input arrays. It does not
interpret units or normalization strings. A fixed or inactive block is not
silently removed: its declared rows remain in the deterministic layout so a
client can change activation policy without changing the numbering contract.

The registry's total row vector is the concatenation of blocks in the exact
order supplied to `initialize_equation_objective_registry`. The
`pack_equation_objective_values` action takes a two-dimensional block-local
array `(max_row_count, block_count)` and copies only the declared rows. Its
JVP is the same linear action and its VJP scatters the packed cotangent back
to a zero-padded block array. These actions carry no constitutive formulas and
are therefore suitable for real residuals, complex residuals represented by a
caller-owned real packing, or objective/constraint values.

Assignment uses deep copies of all allocatable metadata. External clients can
inspect a block with `equation_objective_registry_block`; callers should treat
the returned metadata as immutable after initialization and rebuild the
registry when the block topology or ordering changes.

## Provenance and DESC-like clients

This contract is the reusable registry needed by a DESC-like direct
force-balance client: force components, boundary conditions, flux and
rotational-transform constraints, profile terms, quasi-symmetry diagnostics,
and user objectives can be named and packed without putting their formulas in
FortFEM. The intended reference is the public
[DESC documentation](https://desc-docs.readthedocs.io/en/stable/) and the
direct force-balance formulation in
[Dudt and Kolemen (2020)](https://doi.org/10.1063/5.0020743). Those sources are
provenance for an external client, not copied code or a promise to implement
DESC in FortFEM.

The registry is deliberately less ambitious than an optimization framework:
it does not select an optimizer, infer physical units, evaluate a profile, or
differentiate a callback. Such operations remain explicit residual/JVP/VJP
blocks supplied by the client and can be generated by FortSym upstream of
this metadata boundary.
